## 已落地的边界

- PPTX 分析按 presentation 的关系图确定页面顺序，逐页追踪 layout、master、theme、notesSlide；来源 part 和 `extracted`/`derived` provenance 一起保存。
- 形状文本保存为段落和 run，run 保留原始属性与 source XML；可达 notesSlide 只提取正文占位符，页码、日期、页眉页脚等占位符不混入讲稿文本。
- 主题可声明 `agent/theme-rules.json`。Gateway 在编译后的页面顺序上执行首末布局、必选/禁用布局、允许布局和页数规则；`error` 阻断导出，`warning`/`needs-human` 留在校验结果中。
- 规则和主题内容都有摘要。质量报告保存规则摘要与规则问题，导出前检查 deck revision、主题摘要、规则摘要和质量报告是否一致。

## PPTX 导入的四条明确路线

导入决策统一使用以下语义；旧版 `editable`、`reference` 名称只作为兼容别名，不再把三种策略都写成同一种生成行为。

| 路线       | 生成内容                                                 | 允许的声明                                                 |
| ---------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| `tokens`   | 颜色角色、字体方案、画布和来源证据                       | 只承诺品牌 token 可复用，不承诺布局复刻                    |
| `mirror`   | 保留 reference PPTX，并生成关系图、母版/布局候选和对照页 | 适合继续人工编辑源 PPTX；不把候选布局说成可编辑母版        |
| `fidelity` | 以源页面为视觉基准，生成逐页对照和可定位降级报告         | 允许局部图片回退；必须报告文本、字体、裁剪、渐变和动画损失 |
| `standard` | 将已审查的 token、布局和组件注册为 FastPPT 主题          | 只注册通过规则和布局审查的候选，未审查布局保持草稿         |

每条路线都写入 `IMPORT_STRATEGY.json`，并在审批前保持草稿隔离。路线切换只能产生新的决策版本；已锁定的布局和保留策略不能被静默覆盖。

## 执行顺序

### T1：来源分析与候选生成

1. 完成主题色求值：`schemeClr`、alpha/亮度/饱和度变换、`clrMapOvr`、`themeOverride` 和背景样式引用，始终保留原始节点与最终求值的来源关系。
2. 完成占位符继承：页面 → layout → master 的几何、文字样式、填充/线条和字体脚本选择；组变换先保存矩阵，再单独生成扁平化候选，不能用零坐标补齐缺失值。
3. 为每个候选布局生成 source preview、placeholder map、fixed object map 和 `semanticEvidence`。候选置信度只在有可解释证据时出现，不能按布局序号生成。
4. 把 `extracted`、`derived`、`inferred`、`generated`、`user-overridden` 分成独立字段，生成物不得覆盖来源事实。

T1 的验收样例至少包括多母版、多主题、非连续页面文件名、中文/Latin 混排、notes、背景图片、透明裁剪图片和未使用但已注册的 layout。

### T2：同源母版与可编辑导出

1. Vue layout、`native-layouts.json`、PPTX Master/Layout 共用一套 canvas、placeholder、fixed object 几何模型。
2. 新建页、切换布局、修改母版、多母版和多主题都从锁定的 layout definition 生成真实 PPTX placeholder；不存在定义时明确报告 seed geometry 的 partial 能力。
3. 复用 Slidev walker → normalize → capture → build 的分层思想：捕获证据、归一化几何、PPTX 写入和回读检查分开；沿用 qiulishang 的 CJK/Latin run 拆分和布局审计，但字体选择必须来自主题脚本映射。
4. 对每个对象记录 source boundary、实际输出类型、字体映射、降级原因和回读结果。严格可编辑策略遇到非图片对象的图片回退时阻断。

### R1：规则与发布门禁

1. 人类可读 `theme-rules.md` 负责设计原则，机器规则 JSON 负责结构门禁；两者必须在主题注册时同时可读。
2. 规则结果在 validate、preview quality、editable export 和 PPTX 回读报告中复用同一份结构，不允许各入口各自解释规则。
3. warning 与 needs-human 必须在 Web 审查面板显示来源 ruleId、页号、修复建议；只有 error 默认阻断，用户显式批准的例外要写入可追溯 override。
4. 主题内容、机器规则和锁定母版任一变化都使旧质量报告失效；报告必须能回答“按哪个主题、哪份规则、哪个 deck revision 检查”。

## 必须保持的验证层次

- **结构层**：关系无悬空、shape/placeholder 引用有效、规则 schema 有效、页面顺序来自关系图。
- **编辑层**：文本/表格/图表/placeholder 在目标应用中仍可编辑；图片回退和字体替换有逐对象证据。
- **视觉层**：浏览器预览与 PPTX 回渲染逐页对照，记录换行、裁剪、旋转、透明度、背景和层叠偏差。
- **应用层**：LibreOffice 持续回归；PowerPoint、WPS、Keynote 分别记录打开、编辑、播放、保存和再次打开结果。单元测试和 XML 读回不能替代应用验收。
